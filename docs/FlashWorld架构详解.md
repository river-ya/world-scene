# FlashWorld 架构详解

本文基于项目锁定的 FlashWorld 源码、配置与实验记录，说明模块结构、张量形状、三维反馈、量化及两条基线的机制差异。固定版本见第 1 节。

**核心结论：当前 FlashWorld 是一个以 Wan 多视角潜空间生成网络为主干、以像素对齐三维高斯为显式场景表示、在前几轮去噪中通过“解码三维—渲染—重新编码”施加一致性约束的少步生成系统。** 文本提供语义条件，输入图片提供视觉锚点，相机射线提供几何条件；最终输出可重复渲染的三维高斯，而不仅是视频。

## 2. 整体架构

### 2.1 四个相互配合的部分

FlashWorld 可以按四个部分理解：

1. **条件编码**：图片变成 VAE 潜变量，文本变成 UMT5 特征，相机变成逐像素射线表示。
2. **多视角生成**：DiT 同时处理一组目标视角的潜变量，而不是独立地逐张补图。
3. **三维解码与约束**：网络输出辅助特征和预测潜变量，解码成一份高斯集合，再从多个相机渲染并编码回潜空间。
4. **交付与展示**：将最后的高斯集合导出为 PLY/SPZ，或沿密集相机轨迹渲染 MP4。

### 2.2 数据流图

~~~mermaid
flowchart TD
    IMG["单张 RGB 图片"] --> PRE["中心裁剪、缩放并更新内参"]
    PRE --> VE["Wan VAE 编码器"]
    VE --> C["48 通道图像条件：写入输入锚点"]
    TXT["用户文本"] --> ST["官方内部 Static 前缀"]
    ST --> T5["UMT5-XXL 文本编码"]
    CAM["目标相机：位姿和内参"] --> NORM["参考相机归一化"]
    NORM --> RAY["6 通道射线图"]
    NOISE["多视角高斯噪声潜变量"] --> CAT["拼接：噪声、射线、图像条件、上轮反馈"]
    C --> CAT
    RAY --> CAT
    FB["上轮三维潜变量和辅助特征"] --> CAT
    CAT --> DIT["Wan DiT：跨视角联合注意力"]
    T5 --> DIT
    TIME["当前扩散时间"] --> DIT
    DIT --> V["48 通道 v 预测"]
    DIT --> F["1024 通道辅助特征"]
    V --> Z["预测干净潜变量"]
    Z --> DEC["三维高斯解码器"]
    F --> DEC
    NORM --> DEC
    DEC --> GS["像素对齐三维高斯集合"]
    GS --> RR["前几轮：在生成相机上渲染"]
    RR --> RE["VAE 重新编码为三维一致潜变量"]
    RE --> RN["按下一噪声等级重新加噪"]
    RN --> CAT
    RE --> FB
    F --> FB
    GS --> OUT["最后一轮：PLY、SPZ、密集相机 MP4"]
~~~

该图将重复的前三轮反馈和最后一轮输出画在一起。实际最后一轮直接输出高斯，不再执行下一轮所需的重新编码与加噪。

### 2.3 最需要抓住的关系

**单张输入图负责锚定已有外观，相机条件负责规定观察方向，三维场景表示负责让多个方向的输出相互关联。**

这三件事相互配合，但都不能保证未知区域等于真实房间。未观察区域仍依赖模型从训练数据中学习到的先验。

## 3. 当前模块与参数总表

### 3.1 实际使用的核心模块

| 模块 | 当前实现 | 作用 |
| --- | --- | --- |
| 运行入口 | cli.py → GenerationSystem.generate | 解析输入、调用生成、导出 |
| 文本编码 | T5TokenizerFast + UMT5EncoderModel | 把用户文本映射为语义特征 |
| 图像编码 | AutoencoderKLWan 的 encoder | 编码输入图片，以及三维渲染结果 |
| 几何条件 | normalize_cameras、create_raymaps | 将相机转成模型可用的几何信号 |
| 生成主干 | WanTransformer3DModel | 对整组视角联合预测 |
| 三维解码器 | WANDecoderPixelAligned3DGSReconstructionModel | 从潜变量与辅助特征预测高斯 |
| 高斯预测头 | PixelAligned3DGS | 预测位置相关参数、透明度、尺度、旋转及球谐颜色 |
| 可微渲染 | gaussian_render + gsplat.rasterization | 从高斯和相机得到 RGB/深度 |
| 噪声调度 | MyFlowMatchEulerDiscreteScheduler | 提供时间与噪声等级，并执行重新加噪 |
| 线性层量化 | FluxFp8GeMMProcessor | 减小部分 Transformer 权重的存储开销 |
| 工程封装 | experiment.py、offline_models.py 等 | 离线加载、种子、相机协议、记录和完整性校验 |

### 3.2 基础配置与实际运行配置

| 项目 | 当前值 | 解释 |
| --- | --- | --- |
| 视角数 N | 24 | 多视角生成轴，不是 24 个动态时间状态 |
| 图像分辨率 | H=480，W=704 | 本项目室内实验的主要设置 |
| VAE 潜变量通道 | 48 | 不应套用其他 Stable Diffusion 模型的 4 通道印象 |
| 图像到潜空间缩放 | 16 倍 | 潜变量网格为 30×44 |
| 辅助特征通道 | 1024 | 送给高斯解码器，并用于下一轮反馈 |
| DiT 层数 | 30 | 来自实际缓存的 transformer/config.json |
| 注意力头数 | 24 | 每头维度 128 |
| DiT 隐藏维度 | 3072 | 24×128 |
| FFN 中间维度 | 14336 | Transformer 前馈网络宽度 |
| DiT patch | 1×2×2 | 视角轴不合并，空间轴再各缩小 2 倍 |
| patch 后 token 数 | 7920 | 24×15×22 |
| 实际 DiT 输入通道 | 1174 | 包括图像条件、射线和反馈，不是基础配置里的 48 |
| 实际 DiT 输出通道 | 1072 | 48 通道 v 预测 + 1024 通道辅助特征 |
| 推理网络调用次数 | 4 | 对应四个噪声等级 |
| 高斯预测网格 | 240×352 / 视角 | 不是直接在 480×704 上每像素预测两个点 |
| 每网格位置高斯数 | 2 | 共有 24×240×352×2 个高斯 |
| 球谐阶数 | 2 | 每个高斯 27 个球谐颜色系数 |
| 最终每高斯参数数 | 38 | 位置 3 + 不透明度 1 + 尺度 3 + 四元数 4 + 颜色 27 |

这些形状针对当前固定实现、704×480 和 24 视角；改变分辨率或模型版本后不能原样照搬。

## 4. 输入与预处理

### 4.1 JSON 输入

当前 CLI 主要读取：

~~~text
image_prompt    图片路径或 base64 图片
text_prompt     用户文本
resolution      [N, H, W]
image_index     输入图片对应的相机索引
cameras         目标相机列表
~~~

单个相机包含：

~~~text
quaternion = [qw, qx, qy, qz]
position   = [tx, ty, tz]
fx, fy, cx, cy
~~~

工程额外保存的 _camera_control、_lucid_camera 等字段用于协议与记录，不是 DiT 自动识别的额外语义通道。

### 4.2 图片裁剪与内参必须一起变换

原图大小为 \(W_0\times H_0\)，目标大小为 \(W\times H\)，CLI 选择缩放比例：

\[
s=\max(H/H_0,\ W/W_0).
\]

先按目标宽高比中心裁剪，再缩放到目标大小。若裁剪左上角为 \((l,t)\)，则：

\[
f'_x=s f_x,\quad f'_y=s f_y,\quad
c'_x=s(c_x-l),\quad c'_y=s(c_y-t).
\]

这一步会改变像素对应的射线。如果图片裁剪相同但内参未相应调整，两模型看到的有效视野就不同。

本次同条件执行包使用 LucidDreamer 保存的已裁剪 PNG 和有效内参，使 FlashWorld 的再次预处理成为恒等变换，避免重复裁剪带来比较偏差。

### 4.3 图像数值范围与锚点

图片转成 RGB 张量后，像素从 0–255 映射到 \([-1,1]\)，再交给 VAE。输入图只占 24 个视角中的一个锚点，其他视角没有真实 RGB 输入。

因此“生成 24 个视角”并不表示输入了 24 张真实图片。其余视角主要由模型根据单图、文本和几何条件推断。

## 5. 相机、射线与几何条件

### 5.1 相机的 11 维表示

CLI 将相机编码为：

\[
c_i=[q_w,q_x,q_y,q_z,t_x,t_y,t_z,f_x/W,f_y/H,c_x/W,c_y/H].
\]

前 7 维描述姿态与位置，后 4 维是相对图像尺寸归一化的内参。数学上不能把相机旋转四元数的四个数视为普通欧氏位置直接插值；旋转使用专门的四元数插值。

### 5.2 参考相机与平移归一化

normalize_cameras 会：

1. 把四元数和位置转成 c2w 矩阵。
2. 默认以列表的第一个相机作为坐标参考。
3. 将所有相机变换到该参考系。
4. 用平移尺度加 0.01 归一化位置。

\[
\widetilde T_i=T_0^{-1}T_i,\qquad
\widetilde{\mathbf t}_i=
\frac{\mathbf t_i^{\mathrm{relative}}}{T_{\mathrm{norm}}+0.01}.
\]

**参考坐标相机和输入图片锚点是两个概念。** 当前新协议恰好把两者都设为 index 0，但不能认为所有历史输入都如此。

### 5.3 纯旋转为什么需要工程中的参考尺度

所有相机中心相同时，原始代码自动计算的平移范围为 0。归一化本身因分母有 0.01 不一定报错，但导出时会将高斯坐标和尺度乘回 T_norm；如果 T_norm 为 0，导出几何会退化。

当前 camera_control.py 在指定协议下提供正参考尺度，并在生成、渲染和导出间保留同一个尺度。这是当前工程的重要适配；它不是新增的生成网络。

### 5.4 射线图的准确含义

create_rays 在每个像素中心使用 \(u+0.5,v+0.5\) 构造相机射线，并经相机旋转得到单位方向 \(\mathbf d\)，射线原点为相机位置 \(\mathbf o\)。

create_raymaps 输出的六维量是：

\[
\mathbf r=
\left[
\mathbf d,\;
\mathbf o-(\mathbf o^\top\mathbf d)\mathbf d
\right].
\]

后 3 维表示射线上距参考原点最近的点。它与一般介绍中常见的 \([\mathbf d,\mathbf o\times\mathbf d]\) 写法不同；分析当前实现时应采用实际代码中的表达式。

射线图形状为：

\[
[B,6,N,H/16,W/16]=[1,6,24,30,44].
\]

网络由此知道每个潜空间位置朝哪个方向观察、相机之间如何关联，而不只是接收一个笼统的“左转”文本。

### 5.5 当前纯旋转样例的含义

固定相机中心时，归一化原点为零，射线表示的后 3 个分量也为零；不同视角仍通过方向与 RoPE 索引区分。

这类实验主要观察原视野外的场景扩展。由于没有平移视差，不能仅凭纯旋转视频平滑，就证明物体背面、真实深度和遮挡关系已经重建正确。后续若检查三维几何，应增加受控平移或遮挡解除的视角。

## 6. 文本编码与图像编码

### 6.1 文本：UMT5，而不是 CLIP 文本编码器

当前配置为 UMT5-XXL 的编码部分：

| 配置项 | 数值 |
| --- | --- |
| d_model | 4096 |
| num_layers | 24 |
| num_heads | 64 |
| d_ff | 10240 |
| 运行时最大文本长度 | 512 token |

文本特征主要形状为 \([B,512,4096]\)，再经过 DiT 的条件嵌入层映射到主干所需维度。超长文本会截断；padding 位置按当前代码处理为零特征后进入后续网络。

GenerationSystem.generate 会在用户文本前加入官方内部的 **[Static]** 前缀。这表示当前生成目标是静态场景。用户输入文本相同，不等于两种不同模型内部实际编码的字符串完全相同；同条件对比中已明确保留这一模型专用设置。

### 6.2 图像：经过 VAE 编码，写入指定视角的条件潜变量

当前主路径没有额外调用 CLIP 图像编码器。虽然通用 Transformer 类保留可选图像特征分支，当前基础配置 image_dim 和 added_kv_proj_dim 均为空。

图像条件的主要流程：

~~~text
RGB [1,3,480,704]
  → 加入长度为 1 的时间维 [1,3,1,480,704]
  → VAE encoder 与潜分布采样
  → [1,48,1,30,44]
  → 按 mean/std 归一化
  → 写入 condition_latents 的 image_index 位置
~~~

其他 23 个位置的图像条件初始化为零。代码里创建了 masks 变量，但在当前 generate 路径中，它没有再作为额外独立通道拼到 DiT 输入；不能因此把输入通道数再加 1。

### 6.3 VAE 的 patchify 与空间压缩

实际缓存的 VAE 配置：

- z_dim=48。
- patch_size=2。
- 基础 encoder 通道 160，decoder 基础通道 256。
- 空间缩放配置为 16。

patchify 先将 RGB 的 2×2 空间块折叠到通道，因此 VAE 配置中的 in_channels=12 是 \(3\times2\times2\)，不代表输入图片有 12 个颜色通道。

其空间尺寸可以理解为：

~~~text
RGB：480×704，3 通道
  → patchify：240×352，12 通道
  → 三次空间降采样
  → latent：30×44，48 通道
~~~

### 6.4 为什么 24 个视角没有压缩成 6 个时间位置

基础视频 VAE 原本包含时间压缩设计，app.py 也保留 temporal_downsample_factor=4 属性。但当前 FlashWorld 路径把每张视图作为长度为 1 的样本编码，三维渲染后同样将 B×N 展成单视图批次再编码。

因此本例的 DiT 张量仍有 24 个视角位置，不是先变成 6 个位置再生成。源码还调整了因果卷积与重建解码器的时间相关组件，不能直接照搬原视频 VAE 的完整视频压缩流程来解释当前路径。

### 6.5 潜变量归一化

设 VAE 潜变量为 \(z\)，每通道固定统计量为 \(\mu,\sigma_z\)，则：

\[
z_{\mathrm{norm}}=(z-\mu)/\sigma_z,\qquad
z=z_{\mathrm{norm}}\sigma_z+\mu.
\]

这里的 \(\sigma_z\) 是 VAE 的通道统计量，和扩散噪声等级 \(\sigma_t\) 是不同概念。两者混淆会导致对“去噪”“反归一化”的错误理解。

VAE 使用潜分布的 sample，而非始终取确定性的 mode，因此随机种子也影响这一部分。

## 7. DiT 主干内部结构

### 7.1 初始化与专用权重加载

GenerationSystem 先从 Wan 基础组件初始化网络，再扩展输入、输出和反馈结构，最后加载 FlashWorld 专用 checkpoint 中的 transformer 与 recon_decoder 权重。

这些新增通道不是每次推理都以随机值独立工作：初始化时的填零或随机扩展会被已训练的专用权重覆盖。遗漏专用 checkpoint，不能得到等价的 FlashWorld。

### 7.2 Patch embedding

有效输入形状：

\[
[1,1174,24,30,44].
\]

使用 kernel/stride 为 \((1,2,2)\) 的 Conv3d，得到：

\[
[1,3072,24,15,22].
\]

随后将视角与空间维展平：

\[
[1,7920,3072].
\]

这 7920 个 token 包含全部 24 个视角。因而当前主干有机会同时协调不同视角的内容。

### 7.3 一个 Transformer block 的顺序

~~~mermaid
flowchart LR
    X["输入 token"] --> N1["归一化及时间调制"]
    N1 --> SA["跨视角空间自注意力"]
    SA --> R1["门控残差"]
    R1 --> N2["归一化"]
    N2 --> CA["对文本的交叉注意力"]
    CA --> R2["残差"]
    R2 --> N3["归一化及时间调制"]
    N3 --> FF["前馈网络"]
    FF --> R3["门控残差与输出"]
~~~

30 个 block 重复上述结构：

- **Self-attention**：视角间与空间位置间的信息交换。
- **Cross-attention**：将文本语义注入视觉 token。
- **FFN**：对特征进行非线性变换。
- **时间调制**：按当前噪声阶段调整特征的偏移、缩放和残差门控。

“3D Transformer”在这里首先指处理视角×高×宽的特征组织，并不表示它直接在一个三维体素网格上卷积。

### 7.4 注意力不是逐帧因果生成

当前注意力调用使用 is_causal=False。Self-attention 的 token 序列覆盖全部视角，没有把第 i 个视角限制成只能看前 i−1 个视角。

因此更准确的描述是“整组多视角联合生成”。视频的播放顺序不等于网络按照同样顺序逐帧生成。

### 7.5 三轴 RoPE

WanRotaryPosEmbed 为视角索引、空间高度、空间宽度分别构造旋转位置编码，然后组合到每个 token 上。每头 128 维在当前实现中按 44/42/42 分配到这三个轴。

RoPE 表示序列和网格位置；相机射线表示真实姿态与成像几何。**RoPE 不能替代相机条件。**

### 7.6 文本、时间与额外图像分支

当前模型使用：

- 4096 维文本输入，通过条件嵌入映射到主干维度。
- 频率维度 256 的时间嵌入，再产生各 block 使用的调制量。
- 可选的独立图像特征交叉注意力接口在当前配置中未启用。

因此不能把别的 I2V 模型中的 CLIP 图像 token、CFG 双分支等结构未经核对就添加到本架构图中。

### 7.7 输出与 unpatchify

投影层在每个空间 patch 上输出 \(4\times1072=4288\) 个数，再恢复 2×2 空间位置，形成：

\[
[1,1072,24,30,44].
\]

恢复后的 1072 通道按 48 与 1024 分开。它不是直接的 RGB 视频输出。

## 8. 1174 输入通道与 1072 输出通道

### 8.1 输入通道逐项相加

| 输入内容 | 通道数 | 作用 |
| --- | ---: | --- |
| 当前带噪潜变量 | 48 | 当前要更新的多视角状态 |
| 相机射线图 | 6 | 几何条件 |
| 输入图片条件 | 48 | 锚点位置包含真实图片潜变量 |
| 上轮辅助特征 | 1024 | 前一轮的中间生成信息 |
| 上轮三维潜变量 | 48 | 前一轮经高斯渲染与重新编码得到的反馈 |
| 合计 | **1174** | 当前有效输入通道数 |

第一轮上轮反馈均为零。后续轮次填入上一轮计算结果。

代码先将基础 patch embedding 从 48 扩展到 102，再通过反馈模块扩展到 1174。手动扩展权重不一定同步更新原始配置对象或模块显示属性，因此只阅读基础 config.json 中的 in_channels=48 会漏掉实际结构。

### 8.2 输出通道的职责不同

| 输出 | 通道数 | 后续用途 |
| --- | ---: | --- |
| v_pred | 48 | 与当前带噪潜变量和噪声等级组合，预测干净潜变量 |
| feats | 1024 | 为三维高斯解码提供辅助特征，并反馈到下一轮 |

v_pred 对应 flow-matching 的速度预测，不能简单称为“预测 RGB”或“预测深度”。

若当前带噪潜变量为 \(z_t\)，噪声等级为 \(\sigma_t\)，则实现中的二维分支干净估计为：

\[
\widehat z_0^{2D}=z_t-\sigma_t v_\theta.
\]

这里的“二维”表示直接由扩散输出得到的多视角潜变量；后面还会经三维表示与渲染得到另一份潜变量。

## 9. 三维高斯解码器

### 9.1 输入既有潜变量，也有辅助特征

重建解码器每次接收：

- 反归一化后的 48 通道潜变量。
- 1024 通道辅助特征。
- 各视角对应的相机参数。

视角先展入批次：

~~~text
latent：[1,48,24,30,44]   → [24,48,1,30,44]
feats ：[1,1024,24,30,44] → [24,1024,1,30,44]
~~~

解码器不是只根据 RGB 做一个独立的传统多视图重建。它直接接收生成主干内部的高维特征。

### 9.2 从 Wan VAE decoder 继承，再改成高斯特征解码器

当前实现会：

1. 复制基础 VAE 的 decoder 和 post_quant_conv。
2. 增加 extra_conv_in，将 1024 通道辅助特征投影到解码器入口。
3. 将潜变量分支和辅助特征分支相加。
4. 经过中间残差模块与空间上采样模块。
5. 移除原来的 RGB 输出卷积，输出高斯头需要的特征。

入口可以简写为：

\[
x_{\mathrm{dec}}=
\mathrm{Conv}_{z}(\mathrm{PostQuant}(z))
+\mathrm{Conv}_{f}(F).
\]

当前 decoder_base_dim=256，入口特征宽度为 1024，最终高斯头输入宽度为 256。

### 9.3 为什么最后是 240×352，而不是 480×704

重建解码器从 30×44 经过三次 2 倍空间上采样：

~~~text
30×44 → 60×88 → 120×176 → 240×352
~~~

原 RGB VAE 路径在最后还可使用 patch_size=2 的 unpatchify 恢复全分辨率 RGB；高斯重建路径没有执行这一步，而是在 240×352 特征网格上接高斯预测头。

这里很容易把“全分辨率输出视频”与“高斯预测网格分辨率”混为一谈。视频仍渲染到 480×704，但高斯预测网格是其一半宽高。

### 9.4 两个高斯与总点数

高斯头使用一个 3×3 Conv2d，每个网格位置输出 2 组局部参数，共 76 个通道。

\[
N_G=N\times H_G\times W_G\times2
=24\times240\times352\times2
=4{,}055{,}040.
\]

**这是约 405 万个候选高斯，不是 24 张 RGB 图片。**

本地两个实际 FlashWorld PLY 文件头均记录 element vertex 4055040，与上述推导一致。默认 CLI 使用 opacity_threshold=0，不执行正阈值透明度筛选，因此这个数量被完整导出。

不同视角预测的点会汇入同一高斯集合，但代码没有因此保证它们在物理上绝不重复；相邻视角仍可能产生相近或重叠的高斯。

## 10. 高斯参数的数学含义

### 10.1 局部预测与最终参数

| 局部输出 | 数量 | 处理 |
| --- | ---: | --- |
| 球谐颜色 | 27 | 2 阶球谐，9 个基函数×RGB |
| 射线位置偏移 | 2 | 调整预测点所依附的成像射线 |
| 深度相关量 | 1 | 指数激活，得到正的射线距离 |
| 不透明度 | 1 | sigmoid |
| 高斯三轴尺度 | 3 | sigmoid 与像素相关尺寸结合 |
| 高斯旋转 | 4 | 四元数归一化 |
| 局部合计 | **38** | 其中偏移 2 + 距离 1 最后转成 xyz 3 |

最终每个高斯仍为 38 维：

\[
G_j=(\boldsymbol\mu_j,\alpha_j,\mathbf s_j,\mathbf q_j,\mathbf h_j).
\]

局部参数中的“高斯旋转四元数”和相机输入中的“相机四元数”属于不同对象，不能混用。

### 10.2 中心位置：由射线约束，而不是任意回归 xyz

设预测的正距离为 \(d_j=\exp(\widehat d_j)\)，修正后的单位射线方向为 \(\mathbf d_j\)，原点为 \(\mathbf o_j\)，则：

\[
\boldsymbol\mu_j=\mathbf o_j+d_j\mathbf d_j.
\]

这使高斯位置与相机成像关系直接关联，有助于形成可解释的几何结构。

因为射线方向经过单位化，此处 d 的含义更接近沿射线的距离。它不能未经转换就等同于某个渲染器输出的相机 z 深度，更不能直接当成有真值标定的米制距离。

### 10.3 高斯的体积、方向与颜色

高斯由三轴尺度和旋转控制空间协方差，可概念化为：

\[
\Sigma_j=R(\mathbf q_j)
\mathrm{diag}(s_{j,x}^2,s_{j,y}^2,s_{j,z}^2)
R(\mathbf q_j)^\top.
\]

它可以覆盖一个有方向和体积的区域，不是只在单个像素位置显示一个离散点。

球谐系数允许颜色随观察方向变化。其能力仍受训练和表示限制；存在球谐颜色并不意味着镜面反射就一定正确。

### 10.4 尺度计算要以实际源码为准

当前实现先按网格尺寸计算一个与焦距、深度有关的 pixel_size，再与 sigmoid 激活后的三轴尺度相乘。若使用归一化焦距 \(\bar f_x,\bar f_y\)，其表达式为：

\[
p=
\sqrt{(\bar f_x/W_G)^2+(\bar f_y/H_G)^2}\;d,
\qquad
s_k=16\,\mathrm{sigmoid}(\widehat s_k)\,p.
\]

这是对固定源码的转写，不应自行用一般针孔模型里常见的另一种像素尺寸公式替换后，仍称其为原始实现。

### 10.5 lrs_mul 的含义

高斯头对不同输出组设置了通道倍率，例如 uv_offset 的倍率为 0.01。这些倍率在前向中乘到投影权重与偏置上。

它不是“推理时执行不同学习率优化”，也不是将偏移硬性限制在 ±0.01。固定通道倍率影响参数化和训练尺度，但输出仍由已训练权重决定。

## 11. 四步推理与三维反馈

### 11.1 四个数组索引对应哪些时间

app.py 中 denoising_steps=[0,250,500,750] 是 scheduler 时间表的索引，不是实际时间值。

当前调度器构造指定 shift=3，初始时间表长度 1000。依照固定 diffusers 代码：

\[
\sigma(s)=\frac{3s}{1+2s},
\qquad
t=1000\sigma.
\]

| 数组索引 | 原始 s | 移位后 σ | 实际时间 t |
| ---: | ---: | ---: | ---: |
| 0 | 1.00 | 1.00 | 1000 |
| 250 | 0.75 | 0.90 | 900 |
| 500 | 0.50 | 0.75 | 750 |
| 750 | 0.25 | 0.50 | 500 |

因此不能把这四步解释成“先在 t=0 去噪，再到 t=750 加噪”。实际访问的是从高噪声到较低噪声的时间序列。

固定基础缓存的 scheduler_config.json 虽写有 UniPCMultistepScheduler，但当前代码显式构造的是 MyFlowMatchEulerDiscreteScheduler，不能仅据缓存里的类名判断实际算法。[固定版本调度器源码](https://github.com/huggingface/diffusers/blob/447e8322f76efea55d4769cd67c372edbf0715b8/src/diffusers/schedulers/scheduling_flow_match_euler_discrete.py)

### 11.2 前三轮执行的闭环

对前三个时间点，代码执行：

1. DiT 联合预测当前整组视角的 v_pred 与辅助特征。
2. 得到直接的干净潜变量估计。
3. 使用潜变量与辅助特征解码出高斯集合。
4. 从 24 个生成相机渲染同一份高斯集合。
5. 对 24 张渲染结果重新做 VAE 编码。
6. 归一化，得到三维分支的潜变量估计。
7. 根据下一时间点重新加噪，作为下一轮的输入。
8. 保存本轮辅助特征与三维潜变量，供下一轮条件拼接使用。

符号表示：

\[
G_t=D_G(F_t,\widehat z_0^{2D},C),
\]
\[
\widehat z_0^{3D}=
\mathrm{Norm}\!\left(E(R(G_t,C))\right),
\]
\[
z_{\mathrm{next}}=
(1-\sigma_{\mathrm{next}})\widehat z_0^{3D}
+\sigma_{\mathrm{next}}\epsilon.
\]

这是代码中的重新加噪更新方式。当前路径没有直接调用一个通用 scheduler.step 来完成所有步骤。

### 11.3 为什么这个环节与一致性有关

直接生成的多视角潜变量可以各自偏向不同的纹理解释；但重新编码之前，它们必须先经过一份共同的三维高斯集合和相机渲染。

因此不同视角的结果受到共享表示的约束。该约束能减少彼此任意独立变化的自由度，但不保证高斯几何一定正确。

### 11.4 最后一轮与前三轮不同

最后一轮：

~~~text
DiT → v_pred 与 feats
    → 干净潜变量
    → 高斯解码器
    → 最终高斯集合
    → 密集相机视频及 PLY/SPZ
~~~

没有下一轮需要引导，因此最后不再执行完整的“生成相机渲染—VAE 重编码—重新加噪”循环。

### 11.5 “四步”为什么仍可能计算很多

本例正常视频输出路径中：

- DiT 前向 4 次。
- 高斯解码器前向 4 次，每次处理 24 个视角特征。
- 前三轮反馈各渲染 24 个视角，共 72 次视角渲染。
- 最终视频渲染 346 个相机。

合计约 **418 个视角的高斯渲染**，不包含额外 UI 操作。VAE 还需编码输入图和三批反馈渲染图。

所以“四步”不等于只做四次小型运算，更不等于当前 CPU offload 配置下整个任务一定几秒完成。

### 11.6 与逐视角生成、生成后优化的区别

FlashWorld 的四轮迭代轴是噪声等级，每轮同时更新整组视角对应的状态。它不是每完成一个视角就把该视角当作下一张图的唯一条件。

推理函数处于 no_grad 下，没有针对当前场景的 optimizer.step 或反向传播更新网络权重。三维反馈是推理中的状态更新，不是在线训练。

## 12. 渲染、视频与资产导出

### 12.1 渲染器使用什么

高斯参数经相机变换后进入 gsplat.rasterization。当前实现：

- 将 OpenGL 相机约定转换为渲染器所需的约定。
- 使用 classic 栅格化模式。
- 生成 RGB 和深度相关输出。
- 推理路径明确使用白色背景。

场景几何不正确时，共享渲染器仍可以产生平滑视频。因此“无闪烁”和“几何正确”不是相同指标。

### 12.2 24 个生成相机与 346 个视频相机

视频在相邻生成相机间插值：

\[
N_{\mathrm{video}}=(N-1)\times15+1=346.
\]

位置与内参按对应实现插值，旋转使用四元数插值。当前固定中心、固定内参轨迹只保留方向的连续变化。

346 帧不等于模型独立生成了 346 个场景，也不是 346 次扩散调用；它们是从最终场景上渲染出来的连续观察。

### 12.3 PLY、SPZ 与 MP4 的关系

| 格式 | 保存内容 | 用途 |
| --- | --- | --- |
| PLY | 高斯位置、球谐系数、不透明度、尺度、旋转 | 后续查看、渲染与三维交付 |
| SPZ | 打包后的高斯表示 | 更紧凑的分发与展示 |
| MP4 | 沿选定相机渲染的 RGB 序列 | 快速检查视觉质量 |

MP4 不能替代完整三维资产。普通点云查看器也不一定正确解释高斯的尺度、透明度和球谐。

### 12.4 导出尺度与参数激活

导出函数把内部坐标、尺度乘回 T_norm；不透明度转换回 logit，尺度转换到 log 参数，以适配相应格式。

当前 PLY 的颜色系数字段被依次命名为 f_dc_0…f_dc_26；不完全沿用某些其他 3DGS 工具将高阶项命名为 f_rest_* 的习惯。因此第三方查看器兼容性应以实际文件测试，不能只看扩展名。

### 12.5 为什么单个 PLY 很大

本例每个高斯 38 个 float32，主体数据大小：

\[
4{,}055{,}040\times38\times4
=616{,}366{,}080\text{ bytes}.
\]

本地实际 PLY 文件大小为 616,366,988 bytes，差额为文件头。该结果同时核对了高斯数量和参数布局。

因此单文件约 616 MB 是当前密集预测方式的自然结果，不必首先怀疑文件重复写入。

## 13. 训练、蒸馏与推理的区别

### 13.1 论文训练流程的简要定位

论文将训练分为双模式预训练与跨模式后训练，并在后训练中加入分布外图文数据。双模式分别学习多视角图像生成和经高斯渲染的场景生成；后训练用图像质量较好的模式指导三维模式，并通过分布匹配、对抗与跨模式一致性约束改善少步结果。这里是论文方法概述，不是本地训练代码审计。[论文方法部分](https://arxiv.org/html/2510.13678v1#S3)

| 阶段 | 在理解架构时需要记住的作用 |
| --- | --- |
| 双模式预训练 | 建立图文、相机、多视角与高斯解码之间的对应 |
| 跨模式后训练 | 把多视角生成的外观质量传给具有显式三维表示的生成路径 |
| 分布外数据联合训练 | 扩展图文条件和相机轨迹的覆盖范围 |

这些约束解释了模型设计动机；其完整优化器、采样比例与训练调度应查论文和实际训练仓库，不能从当前推理循环反向猜出。

### 13.2 当前推理时加载什么

当前 checkpoint 在代码中读取 transformer 与 recon_decoder 两组专用权重，配合基础 UMT5、VAE 和调度组件。

推理不需要同时实例化论文训练时的真实分布教师、假分布评分网络或判别器。训练知识主要通过最终权重进入推理系统。

### 13.3 看到 .train() 不代表正在训练

初始化代码中部分模块调用了 .train()，但同时设置 requires_grad_(False)，主生成函数也用 no_grad 装饰。

判断是否训练，需要看是否构造损失、计算梯度并执行参数更新，不能只搜索一个 train 字符串。

### 13.4 当前项目尚不能据此声称完成了原论文训练

本地固定源码提供的是已经使用的推理组件和工程入口，没有完整的原论文训练脚本、训练数据预处理与分布式调度闭环。

“已复现推理”“已获得三维输出”“已设计受控对照”与“已复现预训练/蒸馏”属于不同完成层级，需要分别验证。

## 14. 量化、卸载与速度

### 14.1 当前精度是混合的

不能笼统称作“整个 FlashWorld 都是 FP8”。源码可见：

| 部分 | 当前处理 |
| --- | --- |
| UMT5 | 以 float32 加载，可放 CPU |
| Transformer block 的部分 Linear | 替换成 FP8DynamicLinear |
| Transformer 多数激活 | 转为 bfloat16，部分归一化/调制保留更高精度路径 |
| VAE 与高斯解码器 | 在主要生成路径中转为 bfloat16 |
| 高斯几何和栅格化关键输入 | 显式转为 float32 |
| 导出 PLY | float32 参数 |

### 14.2 FP8 权重与原生 FP8 GEMM 是两回事

quant.py 按张量范围缩放并量化权重，前向还动态量化输入。其原生 FP8 矩阵乘分支只在代码判定计算能力至少为 9.0 时启用。

当前目标 RTX 4090 对应 8.9，因此该固定实现走回退分支：把量化数值转回运算精度并调用普通线性运算。

所以可以说当前版本使用了 FP8 权重表示和量化处理；**不能据此宣称本项目 4090 上的 Linear 都在调用原生 FP8 矩阵乘，或获得了相应的理论加速。** 这描述的是本代码的判断逻辑，不是对该 GPU 一切 FP8 能力的概括。

### 14.3 当前为什么大量使用 CPU

experiment.py 为 FlashWorld CLI 明确传入 offload_t5 和 offload_vae。

- T5 在 CPU 编码文本，文本特征再送到 GPU。
- VAE 编码与高斯重建解码器的主要计算也随配置在 CPU 上进行。
- DiT 和相关激活仍使用 GPU。
- 三维反馈中，GPU 与 CPU 之间还要搬运渲染图、潜变量和辅助特征。

前三轮都经过这一闭环，因此卸载的成本会重复出现。CPU 上的高维解码器、主存带宽和数据移动都可能成为瓶颈。

### 14.4 为什么主机内存申请到 96G

加载阶段先建立基础网络、再建立重建解码器、读取专用 checkpoint 并替换权重，随后才量化与调整设备位置。峰值内存不能简单等于最终 GPU 中保存的权重大小。

此外，UMT5、VAE/解码器、潜变量、密集高斯和导出数组也消耗主存。当前 4090 部署配置申请 96G 主机内存，用于模型加载、量化和卸载；运行峰值与稳定阶段的占用不同。

### 14.5 如何理解“论文秒级”和“本项目较慢”

当前设备、卸载策略、冷启动加载和视频导出都与高显存设备上的模型计时条件不同。应分别记录：

1. 环境和模型初始化。
2. 四轮生成与反馈。
3. 密集相机渲染。
4. 三维格式转换与压缩。
5. Slurm 排队时间。

不能把包含 CPU offload、冷启动和视频导出的总任务耗时，直接与不同条件的核心推理数字相减并判断实现是否错误。

## 15. 当前项目封装改了什么

### 15.1 工程层与模型层的边界

~~~text
Slurm 资源申请与日志
    ↓
tools/experiment.py：身份、输入、种子与结果记录
    ↓
offline_models.py：把固定远程 ID 重定向到本地固定快照
    ↓
camera_control.py：必要时提供显式相机参考尺度
    ↓
原始 FlashWorld CLI 与 GenerationSystem
    ↓
PLY / SPZ / MP4 + manifest
~~~

| 工程文件 | 作用 | 是否新增学习模块 |
| --- | --- | --- |
| experiment.py | 输入快照、种子、运行状态、摘要和环境记录 | 否 |
| offline_models.py | 固定本地快照加载、分词器与配置预检 | 否 |
| camera_control.py | 指定相机归一化尺度，特别处理纯旋转导出 | 否 |
| angles.py / wideview.py 等 | 构建受控相机与样例 | 否 |
| lucid_inputs.py | 保存两模型可共用的裁剪图与相机协议 | 否 |
| Slurm 脚本 | 资源隔离、作业提交、日志和临时目录管理 | 否 |
| 同条件执行包 | 冻结输入、复用已有 Lucid PLY、白底重渲染及拼接 | 否 |

因此当前工程成果应描述为可复现封装、离线运行、相机受控实验和结果管理，而不能直接表述为已经修改 FlashWorld 的神经网络主干。

### 15.2 当前锁定资产

FlashWorld 的专用 checkpoint 是模型适配后的权重；Wan 缓存则提供基础 Transformer、VAE、文本编码器、分词器和调度配置。

基础模型名称中有 5B，不代表整个推理系统加上 UMT5、VAE 和重建解码器后总共只有 5B 参数，也不等于全部组件只需 5GB 或 10GB 显存。

### 15.3 记录与验证能保证什么

manifest、文件摘要、source-check 和 preflight 能帮助确认：

- 使用了哪个固定源码与权重。
- 实际输入与种子是什么。
- 输出是否齐全、是否在实验后改变。
- 某个运行是否完成了技术检查。

它们不直接判断几何与视觉质量。技术 complete 与视觉验收通过需要分开。

## 16. 与 LucidDreamer 的差异

### 16.1 两种生成范式

| 比较项 | 当前 FlashWorld | 当前 LucidDreamer |
| --- | --- | --- |
| 主要先验 | 视频/多视角生成主干及学习到的高斯解码 | 图像补全扩散模型与单目深度 |
| 生成组织 | 整组视角联合处理，按噪声等级更新 | 沿目标视角逐步扩展 |
| 新区域来源 | 多视角潜变量与高斯解码共同产生 | 点云投影空缺处的图像补全 |
| 几何来源 | 网络预测射线上的距离与高斯参数 | 对输入/补图估计深度并提升成点云 |
| 一致性机制 | 跨视角注意力、共享高斯渲染反馈及已训练约束 | 已有点云投影、深度与边界对齐 |
| 当前场景优化 | 无逐场景反向优化循环 | 点云构建后执行 2990 步高斯优化 |
| 最终表示 | 三维高斯 | 三维高斯 |

### 16.2 新纹理与误差累积的可能机制

LucidDreamer 的新补图会进入更新后的点云，随后再投影到更远的视角。错误的纹理或深度有机会成为后续条件，形成累积偏差。

FlashWorld 的每一轮同时处理整组目标视角，并通过共同三维表示进行反馈，因此对单个视角独立偏离有不同的约束。

这是与当前实现相符的机制解释，不是断言 LucidDreamer 一定更差，或 FlashWorld 不存在误差传播。FlashWorld 自己也使用上轮反馈，错误场景同样可能被反馈保留。

### 16.3 模糊可以出现在不同阶段

- 潜变量生成阶段：模型先验不足，输出细节本来就不清晰。
- 三维解码阶段：距离、尺度和不透明度不协调，导致涂抹、重叠或浮点。
- 渲染阶段：高斯过大、透明度混合、遮挡处理形成模糊。
- 展示阶段：视频压缩让高频纹理进一步损失。

因此“看着模糊”不能自动归因于训练步数不够，也不应立即用增加迭代次数来处理。

### 16.4 当前同条件样例能回答什么

客厅左转 40° 对照统一了图片像素、用户文本、内参、生成与视频相机、帧率、种子整数和显示背景。它可以检验：此前观感差异是否仍在同条件下出现。

它不能单独给出整个模型的总体排名，也不具有未知区域真实图像监督。文本内部前缀、模型专有算法、数值精度与原生栅格化器仍有差异，记录中应明确保留。

## 17. 能力、局限与实验解释

### 17.1 当前能够支持的任务表述

当前项目主要复现的是：

**给定单张 RGB、文本和目标相机轨迹，生成一份可沿该轨迹观察的静态三维高斯场景。**

输入图、文本和几何条件构成多模态控制，任务属于静态三维场景生成。

### 17.2 当前不能直接声称实现的能力

- 从动作序列预测物体状态演化。
- 学习刚体碰撞、接触或动力学规律。
- 保证未知区域恢复成真实世界的样子。
- 在任意远距离、任意回环、任意平移下保持正确几何。

24 个视角的轴在这里主要是观察位置，不是现实世界时间。静态世界内容生成和动态世界状态预测需要区分。

### 17.3 一致性强不代表几何真

一个错误但固定的三维场景也可以在不同视角下稳定渲染。评价应把以下维度分开：

| 维度 | 检查内容 |
| --- | --- |
| 输入保真 | 原图可见区域是否被保留，颜色与布局是否改变 |
| 语义合理性 | 新物体和材质是否符合文本与已有场景 |
| 空间连贯性 | 墙线、地面、家具连接和遮挡是否合理 |
| 跨视角稳定 | 同一结构是否发生跳变、重复或漂移 |
| 几何可信度 | 有平移时视差是否合理，深度边界是否稳定 |
| 效率 | 在明确卸载与硬件条件下分阶段计时 |

### 17.4 当前最有价值的后续检查

这是实验分析建议，不是已经实现或验证的网络改进：

1. 在同一图文条件与相机上比较两个模型，不混用不同转角的视频。
2. 同时查看输入方向、中段、末段，避免只挑选最好看的帧。
3. 增加一个小平移轨迹，检验纯旋转无法暴露的几何问题。
4. 若检查 FlashWorld 内部失败来源，保存各去噪轮次的三维渲染、距离与不透明度分布，再判断错误何时进入。
5. 若未来修改模型或损失，应另建版本、保持权重与结果身份，先保留当前基线。

本文不执行上述新实验，也不提出未经验证即可提升质量的参数组合。
